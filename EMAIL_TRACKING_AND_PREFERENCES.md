# Email Tracking & Preference Center - Implementation Summary

**Branch:** `feat/email-tracking-preferences`
**Scope:** universal outbound-email audit log (Phase 1), admin Email Tracking UI + Resend delivery webhook (Phase 2), self-serve preference center + admin subscription control (Phase 3).

---

## What Was Built

### Phase 1: Universal outbound email log

**Files:**
- `src/lib/notify/sendEmail.ts` — `sendTrackedEmail()`, the single chokepoint every outbound email funnels through
- `supabase/migrations/20260731000000_create_email_log.sql` — `public.email_log` table
- `scripts/verify-email-log.ts` — end-to-end proof script

Every sender in `src/lib/notify/*` (home care, listings, leads, estimates, SEO report, staged drafts, rollback digest, form-error alerts, feedback requests) plus the cron routes and the admin service-quote routes now send via `sendTrackedEmail` instead of constructing their own Resend client. Each send writes one audit row to `public.email_log` with the **exact rendered HTML/text** that went out, a `category` (see `EmailCategory` in `sendEmail.ts`), optional links to domain entities (`homeowner_id` / `subscriber_id` / `lead_id`), `campaign` metadata, and `sent_by` (admin email when admin-triggered, else `system`).

Logging is **best-effort by contract**: a failed `email_log` insert is swallowed and never changes the send result.

### Phase 2: Admin Email Tracking UI + Resend delivery webhook

**Files:**
- `src/app/api/webhooks/resend/route.ts` — `POST /api/webhooks/resend`
- `src/app/api/admin/emails/route.ts` — `GET /api/admin/emails?category=&status=&q=&limit=` (light list rows)
- `src/app/api/admin/emails/[id]/route.ts` — `GET /api/admin/emails/[id]` (single row incl. full HTML body)
- `src/app/vaca-mgmt/emails/page.tsx` + `src/app/vaca-mgmt/emails/[id]/page.tsx` — admin list + "see exactly what was sent" HTML viewer
- `src/components/admin/AdminSidebar.tsx` / `src/components/AdminContent.tsx` — new **Email Tracking** tab

The webhook receives Resend delivery events (signed with Svix; the signature **is** the auth — unsigned requests are rejected 400), matches them to `email_log` rows by `resend_message_id`, and backfills `delivered_at`, `first_opened_at`/`open_count`, `first_clicked_at`/`click_count`, `bounced_at`, `complained_at`, and `last_event_at`. Status only advances forward (an out-of-order `sent` event can't clobber `opened`); negative terminal states (`bounced`/`complained`/`failed`) are sticky. Events with no matching `email_log` row get a 404 while the event is less than 24 h old (so Svix retries — a fresh event may have raced `sendTrackedEmail`'s post-send insert) and are acked after that cutoff (deliberately unlogged sends, e.g. `log: false`). A **permanent** bounce or spam complaint also **auto-suppresses** the address: every marketing stream is turned off, audited as a `webhook` actor change. Transient/undetermined bounces (e.g. mailbox full) update the log but never suppress. The webhook also handles **contact events** (`contact.updated` / `contact.deleted`): a Resend-side / Gmail-native unsubscribe on a broadcast flows back into our DB and auto-suppresses the marketing streams the same way, so `email_preferences` stays the source of truth (two-way sync). Only marketing streams are suppressed — the transactional `follow_ups` opt-out is never touched by a contact event. Contact-event field shapes are logged on every such event so the assumed payload can be validated against live traffic.

### Phase 3: Email preference center

**Files:**
- `src/lib/preferences/streams.ts` — client-safe stream definitions (`STREAMS`, `StreamKey`, `normalizeEmail`; no Node imports, so `'use client'` components can import it without pulling server code into the browser bundle)
- `src/lib/preferences/preferences.ts` — token helpers, `applyUpdate` audit + legacy sync; re-exports everything in `streams.ts` for server callers
- `supabase/migrations/20260801000000_create_email_preferences.sql` — `public.email_preferences` + `public.preference_events`
- `src/app/preferences/page.tsx` + `PreferencesClient.tsx` — public self-serve page at `/preferences?token=…`
- `src/app/unsub/page.tsx` + `UnsubClient.tsx` — public **tokenless** unsubscribe page at `/unsub` (aliased from `/unsubscribe`); pre-fills from `?email=`
- `src/app/api/preferences/route.ts` — `GET/POST /api/preferences` (token-authenticated)
- `src/app/api/preferences/unsubscribe/route.ts` — footer links + RFC 8058 one-click (List-Unsubscribe) target
- `src/app/api/preferences/unsubscribe-by-email/route.ts` — `POST /api/preferences/unsubscribe-by-email`, the tokenless by-email backend for `/unsub`
- `src/app/api/admin/preferences/route.ts` — admin view/toggle, bulk list, CSV export
- `src/app/vaca-mgmt/preferences/page.tsx` — admin **Subscriptions** tab
- `src/lib/notify/resendAudience.ts` + `src/app/api/admin/broadcasts/sync-suppression/route.ts` — broadcast suppression sync

One row per (lowercased) email governs four **marketing streams** — `home_care`, `buy_remodel`, `announcements`, `newsletter` (labels in `STREAMS`) — plus one **transactional suppression flag**, `follow_ups`, covering lead follow-ups + review-request emails. The first three default **on** and are switched off only on opt-out; `newsletter` is an **affirmative-consent** stream that defaults **off** and flips **on** only on explicit signup (the exit-intent capture → `POST /api/newsletter/subscribe`). The full set of persisted suppression flags is `SUPPRESSION_KEYS` (`STREAM_KEYS` + `TRANSACTIONAL_KEYS`); the marketing cascade (`/unsub`, one-click, broadcasts) iterates `STREAM_KEYS` only, deliberately never flipping `follow_ups`. Lead follow-ups and review requests are commercial in purpose, so CAN-SPAM requires a working opt-out (their footer carries an unsubscribe link + a one-click `List-Unsubscribe` header), but they are treated as transactional in policy: a general marketing unsubscribe does not silence them, and opting out of them does not touch any marketing stream (owner decision 2026-07). Purely transactional mail (verification, estimates, internal notifications, and the service-work emails below) is still not represented and always sends. Authentication for the self-serve page is the `preference_token`, a capability — same trust model as the existing unsubscribe links. The page fails safe: a footer-link unsubscribe arrives as an in-page confirm prompt (nothing changes until the recipient confirms), a failed save reverts the toggle and shows an error-styled message, and a 429/5xx on load shows a retryable "Try again" state instead of the invalid-link screen.

**Tokenless fallback (`/unsub`).** The self-serve preference center requires a signed token, so a recipient who reaches an unsubscribe URL without one — a short link, a mistyped address, a link that never carried a token — would otherwise hit a dead end. `/unsub` (and the `/unsubscribe` alias, a non-permanent redirect that preserves the query string) always lets a recipient opt out by entering their email, satisfying the CAN-SPAM requirement that the mechanism actually works. Submitting turns **every** marketing stream off for that email (via `getOrCreateByEmail` + `applyUpdate`), which cascades to the legacy `homeowners` / `newsletter_subscribers` status the same way any other opt-out does. In **follow-ups mode** (`/unsub?stream=follow_ups`, the link baked into lead follow-up / review-request emails) it instead turns off only the transactional `follow_ups` flag and leaves every marketing stream on — the page renders follow-ups-specific copy making clear other emails are unaffected. The by-email endpoint always answers `200 { ok: true }` for any syntactically valid email so it can't be used to probe whether an address is subscribed, and is rate-limited per IP (20/min) to blunt row-creation abuse.

How each stream is enforced:
- **home_care** — the newsletter sender passes `preferenceStream: 'home_care'` to `sendTrackedEmail`, which skips suppressed recipients (logged as `skipped`/`unsubscribed` so the admin sees the intentional non-send) and attaches per-recipient `List-Unsubscribe` + one-click headers. Stream-governed sends are strictly single-recipient — a multi-recipient send with a `preferenceStream` is rejected and logged as `error` (suppression and the unsubscribe token are per-recipient).
  The monthly Home Care cron (`GET /api/cron/home-care-newsletter`) additionally reads the whole `home_care` opt-out list once per run (`getSuppressedEmails`, a read-only paginated select) and classifies every recipient against it, so a `?dryRun=1` reports the buckets a live send would produce.
  A recipient that snapshot already flagged is still handed to `sendTrackedEmail` with `knownSuppressed: true` rather than dropped at the call site, so the honored opt-out leaves the same `skipped`/`unsubscribed` `email_log` row any other suppression leaves - without it an honored unsubscribe is indistinguishable from a member the run never reached.
  `knownSuppressed` is refused ahead of the per-recipient preference lookup, which fails **open**, so a DB hiccup can't turn a known opt-out into a delivered email; the type only admits it alongside a `preferenceStream`, since a verdict about a stream can't exist without one.
  The newsletter footer carries a "Manage email preferences" link, the tokenized unsubscribe link, and (CAN-SPAM) the physical postal address `51 Crestmont Rd, West Orange, NJ 07052`.
  **Every** Home Care email carries that address now, not just the newsletter. Verification, welcome and the release-notes email ran an older 560px shell with a different header and no postal address, so a member could get three emails in a week that looked like three different companies; all of them now render through the shared chrome in `src/lib/homecare/emailShell.ts` (licence bar, brand row, context pill, two-tone headline, orange CTA, navy call block, `footer` + `textFooter`, which is where `BUSINESS_ADDRESS` lives). `buildNewsletter` deliberately still renders its own copy of that chrome - it shipped to production on 2026-07-29 and its first send under the new design is 2026-08-01, so it was not refactored days before that run; `tests/home-care-email-shell.spec.ts` pins the newsletter's chrome against the shared module so the two cannot drift while they coexist, and converging `buildNewsletter` onto `homeCareEmailShell` is a follow-up for after the August send.
  The newsletter's hero image is served from the canonical site host (`NEXT_PUBLIC_SITE_URL`) rather than the request origin, so invoking the cron from a preview deployment can't mail image URLs on a host that 404s; `/email/*` and `/logo.png` are the one exception to the site-wide `Cross-Origin-Resource-Policy: same-origin` in `next.config.ts`, so a webmail client that renders our `<img>` directly instead of proxying it doesn't get a blocked, broken image.
- **buy_remodel** — kept in sync with the legacy `newsletter_subscribers.status` column, which the Buy+Remodel flows already treat as the source of truth (active-subscriber checks). The subscribe-flow emails (verification, welcome) are transactional and always send.
- **announcements** — enforced two ways. The monthly newsletter cron enumerates the identity-table marketing members (Home Care / Buy+Remodel `active` rows) and sends to them single-recipient through `sendTrackedEmail` with `preferenceStream: 'announcements'` (skips opt-outs, attaches the `List-Unsubscribe` header). Resend *broadcasts* send to an audience outside the wrapper, so opt-outs are mirrored onto the audience's `unsubscribed` contact flag — either on demand via `POST /api/admin/broadcasts/sync-suppression { audienceId }` or automatically by the daily `GET /api/cron/resend-sync` cron. Both call `syncAudienceSuppression`, which is **suppress-only by design (CAN-SPAM safety)**: it only ever adds `unsubscribed:true` and never clears it, so a periodic sweep can never resurrect a Resend-side / Gmail-native opt-out; re-subscription is explicit-operator-only in the Resend dashboard. When a fresh opt-in activates (Home Care / Buy+Remodel verification), `addOrUpdateResendContact` adds them to the broadcast audience, mirroring their current `announcements` state so a new opt-in can't resurrect a prior announcements opt-out.
- **newsletter** — an **affirmative-consent** stream (defaults off, on only on explicit signup via `POST /api/newsletter/subscribe`, which records the consent as a `preference_events` row). The monthly newsletter cron unions in every `email_preferences.newsletter=true` subscriber and sends to them single-recipient through `sendTrackedEmail` with `preferenceStream: 'newsletter'` (skips opt-outs, attaches the per-recipient `List-Unsubscribe` header with `stream=newsletter`). Explicit newsletter consent **wins** over the legacy `announcements` gate: a contact who is both an identity-table member and a newsletter signup is gated on `newsletter`, so their send, footer link, and one-click header all agree. It has no legacy identity table, so `syncLegacyStatus` ignores it.
- **follow_ups** (transactional) — lead follow-ups and review requests pass `preferenceStream: 'follow_ups'`, including the post-visit "how did we do" email that `/api/admin/service-quote/complete` sends directly; a recipient who opted out is skipped (logged as `skipped`/`unsubscribed`). The `send-follow-ups` cron additionally **cancels** every remaining pending queue item for that address on opt-out, so an unsubscribe stops the whole remaining sequence, not just the current send - except rows owned by a dedicated sender, which `withoutDedicatedSenders` holds back: a night-before visit reminder for a visit the customer booked is transactional, and a follow-ups opt-out must not silently drop it. Its opt-out is reached only via the follow-ups-mode unsubscribe link / one-click header on those emails — never the marketing cascade. A **won estimate** cancels the drip too: marking an estimate lead **Converted** in the admin Estimates Manager posts the `stop` action at the `nurture` sequence to `/api/admin/follow-ups`, which runs `cancelPendingFollowUps` (`src/lib/notify/cancelFollowUps.ts`) server-side to flip that address's still-`pending` rows to `cancelled` so a customer who already said yes stops getting nudged - no extra step for the owner. Unlike the opt-out cancel, this one is **scoped to the lead-nurture drip types only** (`instant_ack`/`24h`/`48h`/`7d`, in `LEAD_NURTURE_FOLLOW_UP_TYPES`), so a repeat customer's pending review-request rows (`feedback_day0`/`feedback_day3`/`feedback_day7`) in the same queue survive. The email is matched case-insensitively with `ilike` (the queue stores the raw un-normalized address) with LIKE wildcards escaped so it stays literal. The cancel is best-effort: a failure never blocks the status change (that update already committed) - the owner gets a toast telling them to stop the emails from the Follow-ups admin. Scope is `converted` only; `lost` deliberately does not cancel. The **Follow-ups admin** (`/vaca-mgmt/follow-ups`) is the manual equivalent, and is person-centric. All admin `follow_up_queue` access - the list read and every stop/cancel/resend - goes through the server route `/api/admin/follow-ups` (`src/app/api/admin/follow-ups/route.ts`, secret-key `createClient` that bypasses RLS, gated to admins because the path is under `/api/admin/`) via the `src/lib/followups/followUpsApi.ts` client helpers, not the browser Supabase client. This mirrors the leads/homeowners pattern and is required because `follow_up_queue`'s RLS grants only the `anon` role and not the logged-in `authenticated` role the admin browser uses, so a direct browser read returned zero rows (the list showed all zeros) and a browser-side stop silently no-op'd. Its default **Active drips** tab lists one row per (person, sequence) that still has a pending email - built by the pure `buildActiveDrips` helper (`src/lib/followups/activeDrips.ts`), which groups the fetched `follow_up_queue` rows by person + sequence (`nurture`, `review` and `visit`, kept separate because the queue is shared), soonest-next first, showing who they are, which drip, what's next (label + relative time), and the pending count. Each row has a **confirm-gated** **Stop drip** button that posts `{ action: 'stop', sequence }` to the route, which maps the sequence server-side through the one shared registry (`FOLLOW_UP_SEQUENCE_TYPES` in `cancelFollowUps.ts` - read forward by `followUpTypesForSequence` to scope a cancel, inverted by `followUpSequenceOf` to label a row) and calls `cancelPendingFollowUps`, so stopping one drip never touches another sequence for that address (the client can't pass arbitrary types, and a sequence name the registry doesn't know is refused `400` rather than falling through to the nurture set - which is how a visit-reminder drip's Stop button used to cancel nothing and report "Nothing left to stop" forever). `resend` refuses a dedicated-sender type outright: that generic insert can't carry `visit_start`, so the copy would be a row no cron can ever find. A second **All emails** tab keeps the raw per-email view (with status filters), where each pending/sent row's **Stop follow-ups** button posts the same `stop` action for the sequence the clicked row belongs to (via `sequenceOf()`). Both set the affected rows to `cancelled`; review-request responses are still recorded separately from the Feedback admin. The same scoped stop is also reachable **estimate-side** without changing a lead's status: a **Stop follow-ups** button on the Send Estimate page (`/vaca-mgmt/send-estimate`) and on the Calculator Estimates lead detail (Status & Notes card in `EstimatesManager`) each post the `stop` action at the `nurture` sequence, so review-request emails are never touched. Lead follow-ups 2 (+24 h) & 3 (+48 h) also embed a **Home Care promo** (a "join Home Care" pitch wrapped in the `HC_PROMO_START`/`HC_PROMO_END` markers from `emailTemplates.ts`, with `lead_followup` UTM tags on the `/home-care` CTA); the cron strips just that block at send time — decided live via `isActiveHomeCareSubscriber()` because the body was frozen into `follow_up_queue` 24–48 h earlier — for recipients who are already active Home Care subscribers, and **fails open** (promo kept on any lookup error).
- **service work (two ungated, one on `follow_ups`)** - the three one-visit service emails are the quote (`POST /api/admin/service-quote/send`, category `service_quote`), the night-before visit reminder (`GET /api/cron/visit-reminders`, category `visit_reminder`) and the "Please let us know how our team did" email that mark-complete sends (category `feedback_request`). The quote and the reminder pass **no** `preferenceStream`, so no opt-out can drop them: someone who asked us for a price or booked a window is owed the mail about it, and a reminder for a visit the customer booked is transactional. The completion email is the exception and passes `preferenceStream: 'follow_ups'` - see below. All three are pure builders in `src/lib/homecare/serviceEmails.ts` (`buildServiceQuoteEmail` / `buildVisitReminderEmail` / `buildServiceCompletedEmail`) returning `{ subject, html, text }`, so they can be rendered and asserted without sending anything, and all three reply to `alex@` **and** `veronica@lavacagc.com` (`SERVICE_REPLY_TO`, owner annotation on the service/visit emails only) instead of the shared `info@` mailbox that the rest of Home Care still uses.
  They all carry a working opt-out and the postal address, because CAN-SPAM does not care that we call them transactional. The quote's link is `/unsub?stream=follow_ups`: a quote goes to someone who asked for a price and need never have joined Home Care, so `stream=home_care` claimed a scope the recipient may not have - and `/unsub` branches on `follow_ups` alone, with every other value falling through to the marketing cascade that also turns off `buy_remodel` and `announcements`. Its footer says what the link takes away (the automated follow-up mail about the inquiry) and what it leaves (the quote itself and any scheduling), because beside a quote the safe reading of a bare "Unsubscribe" is "this cancels my quote". The reminder goes to a `homeowners` row that exists by then, so it keeps the tokenized `/api/home-care/unsubscribe?token=`.
  **The completion email is the one that footer is a promise about**, so it carries the same `/unsub?stream=follow_ups` link and is sent **with** `preferenceStream: 'follow_ups'`. Gating it is what makes the sentence true: a recipient who took the offer the quote made in writing is now suppressed rather than sent "Please let us know how our team did", and the visible link, the one-click `List-Unsubscribe` header and the send gate all target the same flag. The tokenized Home Care link would not have done it - that one governs the seasonal programme a service customer may never have joined. An opted-out customer getting no review request is the correct outcome; they asked not to be emailed. `/complete` reports that as `feedback: 'suppressed'`, distinct from `'failed'`, and the admin page says "this customer opted out of follow-up emails" instead of showing an error to retry. The same opt-out also stops the queued `feedback_day0`/`day3`/`day7` drip and the nurture drip, both sent by `send-follow-ups` with the same stream.
  The Google rating in the quote's credibility block is a single exported constant (`GOOGLE_RATING`), never inlined, so an email can't keep claiming 5.0 after the real rating moves; a test asserts the constant is exported and the rating is nowhere inlined in that module.
- **visit reminders in `follow_up_queue`** - scheduling a visit queues one `visit_reminder_1d` row, which is both the queued email and the send-once ledger `/api/cron/visit-reminders` claims against, keyed to its visit by `visit_start` (not `scheduled_at`, which is the same 7:30pm instant for every visit that day). That makes it the third sequence sharing the table, and the only one delivered by its own cron: `DEDICATED_SENDER_FOLLOW_UP_TYPES` lists it, and **both** generic drains read the queue through `sharedFollowUpQueue`, which composes the exclusion onto the query builder rather than trusting each drain to remember a constant. `GET /api/cron/send-follow-ups` (09:00 UTC) would otherwise mail the reminder a second time at ~4am Eastern on the day of the visit, saying "tomorrow"; `/api/follow-up` (the admin "process follow-ups" button) flips due rows straight to `'sent'` without mailing anything, and both `'sent'` and `'responded'` read as closed to the reminder cron's ledger, so it would swallow the email instead. `createLeadFollowUpSequence`'s "has this lead already been through the drip?" check is scoped to the nurture types for the same reason - type-blind, a hand-booked service customer's reminder row suppressed the acknowledgement email for the website form they submitted later.

Every stream change is audited in `preference_events` (old/new value, actor `self | admin | webhook | system`, actor detail, IP). Changes also sync the legacy status columns (`homeowners.status`, `newsletter_subscribers.status`) both ways: the old single-purpose unsubscribe links (`/api/home-care/unsubscribe`, `/api/buy-and-remodel/unsubscribe`) now write through to `email_preferences` too. Re-enabling a stream only promotes `unsubscribed` legacy rows back to `active` — `pending` rows stay pending until they complete double opt-in verification.

## API Routes

| Route | Auth | Purpose |
|---|---|---|
| `POST /api/webhooks/resend` | Svix signature (`RESEND_WEBHOOK_SECRET`) | Delivery events → `email_log` backfill + permanent-bounce/complaint auto-suppress; `contact.updated`/`contact.deleted` → mirror a Resend-side unsubscribe back into `email_preferences` (marketing streams only) |
| `GET/POST /api/preferences` | `preference_token` | Self-serve page: read / update streams |
| `GET/POST /api/preferences/unsubscribe` | `preference_token` | Footer links (GET — mutates nothing, redirects to the preference center with a confirm prompt) + RFC 8058 one-click (POST). `stream=follow_ups` targets only the transactional follow-ups opt-out (GET redirects to `/unsub` follow-ups mode); any marketing link unsubscribes all marketing |
| `POST /api/preferences/unsubscribe-by-email` | none (by email) | Tokenless `/unsub` backend: turns off all marketing streams for the given email (or only `follow_ups` when `{ stream: 'follow_ups' }`); always 200 `{ ok: true }` for a valid email (no subscription probing) |
| `POST /api/newsletter/subscribe` | none (rate-limited, self-guarded) | Monthly-newsletter signup (exit-intent capture backend). Records affirmative consent by flipping the `newsletter` stream on via `applyUpdate` (audited `preference_events` row); seeds a net-new contact's other marketing streams off. Mirrors the contact into the Resend audience honoring its `announcements` state. Always 200 `{ ok: true }` for a valid email (no subscription probing) |
| `GET /api/cron/resend-sync` | Bearer `CRON_SECRET` | Daily suppress-only mirror of `announcements` opt-outs onto the Resend broadcast audience (`RESEND_AUDIENCE_ID`) |
| `GET /api/cron/monthly-newsletter` | Bearer `CRON_SECRET` | Navy/gold newsletter to two unioned audiences, each sent single-recipient through its own gate: identity-table marketing members (Home Care + Buy+Remodel `active` rows) gated on `announcements`, plus affirmative-consent subscribers (`email_preferences.newsletter=true`) gated on `newsletter`. Explicit newsletter consent wins for anyone in both. Per-issue dedup for safe re-runs; `?dryRun=1` counts recipients only. **Deliberately left unscheduled** (not in `vercel.json`) — manual trigger only until the owner confirms the first send |
| `GET /api/cron/home-care-newsletter` | Bearer `CRON_SECRET` | Monthly Home Care seasonal email (1st of each month, scheduled in `vercel.json`), one send per active homeowner per calendar month, gated on `home_care`. Tasks are resolved per member by the shared resolver (`src/lib/homecare/selection.ts` — systems + life-stage gate, minus what they've done, booked, snoozed or dismissed), and each recipient lands in exactly one outcome bucket: `would_send` (of which `caught_up` gets the no-task "all caught up" note), `suppressed`, `empty_skipped`. `?dryRun=1` classifies every recipient and reports the same buckets but writes nothing — no sends, no `email_log` rows, no `last_newsletter_at` touches, no preference-center rows; `suppression_checked: false` flags a dry run that couldn't read the opt-out list |
| `GET /api/cron/visit-reminders` | Bearer `CRON_SECRET` | Night-before service-visit reminder, `30 23 * * *` UTC (scheduled in `vercel.json`) = 7:30pm Eastern in summer, 6:30pm in winter: one fixed UTC time, no DST logic, by owner's choice. Selects visits for **tomorrow in Eastern** (23:30 UTC is still the same Eastern calendar date, so the window resolves correctly; an hour later would silently skip a day) and sends one email per (homeowner, window) listing every service in it. The visit's `follow_up_queue` row is the send-once ledger, claimed `pending`→`sent` **before** the send, so a Vercel retry or a manual GET finds nothing to claim; a send that faults releases the claim, logs per recipient, and answers `ok:false` with `degraded: 'reminder_send_failed'` (nothing revisits it - re-hit before Eastern midnight or text the customer). With `visit_start` not yet migrated there is no ledger, so the run sends **nothing** and reports `degraded: 'reminder_ledger_unavailable'`. `?dryRun=1` classifies and counts, sending and claiming nothing |
| `POST /api/admin/service-quote/send` | admin middleware | Sends the service quote (category `service_quote`) and writes the audit row to `estimate_emails` with `kind='service'` + `scope_summary`/`visit_length`/`valid_until`. Mirrors the project-estimate route: same 30-second idempotency window against a double-click, same audit-on-failure. `isTest` redirects to the owner's inbox and prefixes `[TEST]` |
| `GET /api/admin/service-quote/intake` | admin middleware | Pre-fills the quote form: bookable catalog, the customer's past requests with their task keys parsed out of the lead message, last-done per service, and the visits they currently have on the books (which is what makes "mark completed" reachable in a later session) |
| `POST/GET/DELETE /api/admin/service-quote/schedule` | admin middleware | `POST` books the visit (lightweight `homeowners` row, window onto each task, season derived server-side per task, cancel-then-requeue the reminder) and returns the seasons it filed each task under, the owner's `.ics` URL, and the reminder outcome (`queued` / `skipped` when the covering run has already fired / `unavailable` when the queue could not be reached). A service already booked into a different season is refused `409`. `GET` streams the **owner's** `.ics`, ops alarms included. `DELETE` cancels one window - address read from the homeowner row, never from the caller - and reports whether that visit's reminder was `cancelled` or `unavailable` |
| `POST /api/admin/service-quote/complete` | admin middleware | Marks the booked tasks `done` with `completed_by='lavaca'`, clears the window, cancels that visit's pending reminder, and sends the "how did we do" email (category `feedback_request`, governed by the `follow_ups` opt-out - an unsubscribed recipient is answered `feedback: 'suppressed'`, not `'failed'`). Idempotent: rows already done by La Vaca have had their email, so a second click sends no second one |
| `GET /api/home-care/visit.ics` | `hc_access` cookie | The **customer's** calendar file for their scheduled visit. Hard-codes `variant:'customer'`, so the owner-only ops alarms ("text the customer when the crew is on the way") can never reach a customer |
| `GET /api/admin/emails` | admin middleware | Email log list (filter by `category`, `status`, `q`, `limit`) |
| `GET /api/admin/emails/[id]` | admin middleware | Single email incl. full rendered body |
| `GET/POST /api/admin/preferences` | admin middleware | Contact lookup + audit trail, admin toggles, bulk list (`?all=1`, optional `stream`/`state`; JSON responses carry a `truncated` flag when the `limit` was hit), CSV export (`&format=csv` — paginates to completion, never truncates) |
| `POST /api/admin/broadcasts/sync-suppression` | admin middleware | Mirror `announcements` opt-outs onto a Resend audience |
| `GET/POST /api/admin/follow-ups` | admin middleware | Admin `follow_up_queue` access with the secret key (bypasses RLS, which grants only `anon`). `GET` lists all rows; `POST` handles `stop` (cancel a person's pending rows for one `sequence` — `nurture`/`review`/`visit` — mapped server-side through `followUpTypesForSequence`; an unknown name is `400`, never a silent nurture cancel), `cancel` (one row by `id`), and `resend` (re-queue an email now, refused `400` for a dedicated-sender type such as `visit_reminder_1d`) |

`/api/webhooks/resend`, `/api/preferences`, and `/api/newsletter/` are declared in `PUBLIC_ROUTES` in `src/middleware.ts`.

The public preference endpoints are rate-limited per IP via the existing `rate_limits` table (`src/lib/rateLimit.ts`): `GET /api/preferences` 30/min, `POST /api/preferences` 15/min, unsubscribe `GET` 30/min, one-click `POST` 60/min, tokenless unsubscribe-by-email `POST` 20/min, newsletter subscribe `POST` 10/hour. Over the limit, the JSON endpoints return 429 with a `Retry-After` header; the unsubscribe `GET` instead skips the DB lookup and still redirects to the preference center (the page validates the token itself), so a scanner burst from a shared gateway IP can't break a real click.

## Admin UI

These all live under the existing `/vaca-mgmt` admin, as sidebar tabs:
- **Email Tracking** — every sent email, newest first, with status badges (sent → delivered → opened → clicked; bounced/complained/failed; error = rejected before/while sending, e.g. a misconfigured stream-governed send; skipped = intentional suppression), category/status filters and search; per-row detail view renders the exact HTML that was sent. The category filter tracks `EmailCategory`, so it now also carries **Service quote** (`service_quote`) and **Visit reminder** (`visit_reminder`).
- **Subscriptions** — look up any contact's streams + change history, toggle streams as admin (audited), bulk list with per-stream on/off filters (flagged when it shows only the most recent records), CSV export, and the broadcast suppression sync button.
- **Send Service Quote** (`/vaca-mgmt/send-service-quote`) - the lighter sibling of Send Estimate, for one-visit service work: look a customer up by email, pick services (pre-selected from their own Home Care request, each showing when it was last done and by whom), send the quote, book the visit, download the owner's `.ics`, cancel a window, or mark a booked visit completed. It sits in the sidebar directly beneath Send Estimate, its sibling, and the standalone route keeps working for direct links.
- The **Follow-ups** admin's Active drips tab gains a third sequence, **Visit reminders**, with its own amber pill and a confirm that says plainly what stopping one means (the customer is never told we're coming) rather than calling it a drip.

## Database

Apply these migrations (Supabase dashboard SQL editor or CLI):
1. `supabase/migrations/20260731000000_create_email_log.sql`
2. `supabase/migrations/20260801000000_create_email_preferences.sql`
3. `supabase/migrations/20260805000000_email_prefs_follow_ups.sql` — adds the transactional `follow_ups` boolean column (default `TRUE`) to `email_preferences`
4. `supabase/migrations/20260810000000_email_prefs_newsletter.sql` — adds the affirmative-consent `newsletter` boolean column (default `FALSE`) to `email_preferences`, plus a partial index on `newsletter = true` for the monthly-newsletter recipient query

The three tables those create (`email_log`, `email_preferences`, `preference_events`) have RLS enabled with **no public policies** — access is server-side via `SUPABASE_SECRET_KEY` only.

Home Care service work adds three more, all additive and idempotent, all hand-applied the same way, and no existing column changes type or nullability. Nothing in that feature runs before they land, and what a member can already see degrades rather than breaking: the reminder cron finds no visits, and the checklist page retries its query with the pre-migration column set, so the member keeps their checklist and loses only the visit card and the completion label. The two halves are not interchangeable, though - **booking needs 20260815** (without it the write fails and the request 500s), while the reminder needs 20260816 + 20260817 and degrades on its own: the queue insert 400s, the booking still succeeded, so it is reported as reminder `unavailable` rather than as a failed booking.

5. `supabase/migrations/20260815000000_home_care_service_quotes.sql` - `homeowners.address`/`city` (a street address for the `.ics` `LOCATION`); `homeowner_maintenance.scheduled_start`/`scheduled_end`/`service_address` plus an index on the scheduled window; `homeowner_maintenance.completed_by` (`'homeowner'|'lavaca'`, `NOT NULL DEFAULT 'homeowner'`, CHECK-constrained) so the portal can label the work La Vaca performed; `estimate_emails.kind` (`'project'|'service'`, default `'project'`) with `scope_summary`/`visit_length`/`valid_until`. `estimate_emails.estimate_url` stays `NOT NULL` - QuickBooks stays in the loop for service quotes, so every quote carries a real QBO estimate and the constraint is never violated.
6. `supabase/migrations/20260816000000_visit_reminder_follow_up_type.sql` - widens the `follow_up_queue.follow_up_type` CHECK to admit `visit_reminder_1d`. Without it the reminder insert fails the constraint.
7. `supabase/migrations/20260817000000_follow_up_queue_visit_start.sql` - adds nullable `follow_up_queue.visit_start` plus a partial index, so a reminder row names exactly one visit through the queue, the send-once ledger and the cancel path. Keyed on `scheduled_at` instead, two visits on one date shared a single row.
