## 3. Evaluator - ACCEPT

Independent check: numpy Beta sampling, 2,000,000 draws per case, against the builder's `evaluate()`.

| Fixture | Independent p(beat) / loss | Builder p / loss | Builder verdict |
| --- | --- | --- | --- |
| A 15/300, B 45/300, 20 days | 0.99998 / 0.000000 | 1.0 / 0.000000 | winner B |
| A 3/50, B 8/50, 5 days | 0.9391 / 0.001714 | 0.9441 / 0.001574 | not_enough_data, ready 2026-12-01 |
| A 45/300, B 15/300 | 0.00002 / 0.0994 | 0.0 / 0.0989 | control_wins, retire B |
| A 20/200, B 26/200 | 0.8245 / 0.003033 | 0.826 / 0.003020 | keep_running |
| 3 arms A 30, B 9, C 32 of 300 | B 0.00023, C 0.6051 | B 0.0003, C 0.6054 | retire_losers [B] |

All within Monte Carlo error.
Revenue per visitor: $6,000 / 200 = 3000 cents and $10,500 / 200 = 5250 cents, exact; revenue sums `job_paid` only (`store.server.ts`), so a quote and its payment are not double counted.
The ready date checks by hand: 50 visitors in 5 days is 10 a day, 150 more take 15 days, so 2026-12-01; at 20 days it is 2027-01-15.
Notes, not blockers: the "same rates at 50" fixture is 6% versus 16%, not the 5% versus 15% of the 300 fixture, and its p (0.944) is below 0.95 anyway, so it does not by itself prove the sample guard overrides a winner; the code checks the guard first, which I read.
`p = 1.0` prints as "100.0%", which overstates a Monte Carlo estimate; "more than 99.9%" would be honest.

## 4. Cron, veto window, veto link - mechanics ACCEPT

On the production build with two backdated running fixtures (300 visitors per arm, 15 versus 45 requests, started 20 days ago):

- No `Authorization`: 401.
- Run at fake T0 `2026-11-02T07:30Z`: both `proposed`, `pending_promotion`, `telegram: not_configured`, message with `Veto: http://localhost:3126/experiments/veto/<token>`.
- GET the veto page twice with a browser UA and once as `facebookexternalhit`: 200 each, `noindex, nofollow`, both rows still `pending_promotion`.
- POST `/api/experiments/veto` with a tampered token: 410; with the real token: 200 `{ vetoed: true, kept: "A" }`; the same token again: 410 "There is no promotion waiting on this link any more."
- Run at T0 + 23h59: `waiting_for_veto_window`; the vetoed one is not listed.
- Run at T0 + 24h01: `promoted`, control B, `decision.promoted.by = "cron (after the 24 hour veto window)"`; the vetoed one stays concluded with control A.

Two issues the specs do not catch:

- F3: a proposal enters the veto window whether or not Alex was told.
  `proposeWinner` sets `pending_promotion` and the cron later promotes it even when the Telegram outcome is `failed`, `not_configured`, or the veto URL is null (no `INTERNAL_WEBHOOK_SECRET`).
  Decision 005 Q15 is "promotes after a 24-hour Telegram veto window"; a window nobody was notified of is not one.
- F6: the message says the wrong time.
  The cron runs weekly (`30 7 * * 1`), so a winner proposed Monday 07:30 is promoted the next Monday, not "at 2026-11-03 07:30 UTC" as the Telegram message and the admin card say.
  `docs/experiments.md` says it correctly ("the next run after 24 hours").

## Fix list

Required before ACCEPT:

- F1 (hard rule): refuse prices in copy however they are written.
  At minimum: a currency sign before or after a number including full-width `＄`, `bucks`, number words followed by dollars or dólares, and any bare number of three or more digits in a copy slot (the site's copy has no legitimate use for one; "seven" and "24/7"-style text survive).
  Add "free", "half price", "discount", "off", "deal", "save" and the Spanish equivalents as discount words.
  Add these cases to the EX6 live test and the unit test.
- F2: run the variant `label` through the same `forbiddenClaim`, because `heroStore.server.ts` renders `v.label` as the homepage button wording when the payload has no `wording` (a `color`-only variant labelled "$99 off" would show "$99 off" on `/` once the Phase 1 pair concludes).
- F3: do not enter `pending_promotion` unless the Telegram send succeeded and the veto URL exists; otherwise record the verdict, keep the experiment running, and report "proposal not delivered" so the next run retries.
- F4: make the preview test independent of the language cookie (`&lang=en`, or clear `lv_lang` before that step); it fails deterministically on a production build.
- F5: name `RECAPTCHA_E2E_BYPASS_TOKEN` (and `bypassCSP` for a production build) in the spec header's run line, or skip EX3 with a reason when the token is unset.
- F6: say when a pending winner will really be promoted (the next weekly run after the window, a date), in the Telegram message and the admin card; or run the promotion step daily.

Recommended:

- F7: on phones, show Sent, Rate and Beats control first (or stack the arms), and preselect the evaluator's leader for Promote with a non-primary style when there is no winner.
- F8: add drafts, current-copy lookup, the `sections` mapping and a safe `--site` default (or a confirmation for production) to the skill.
- The specs leave `view` rows on `hero-primary` and `hero-secondary` after each run on the shared rig (I removed 34 rows from my runs); clean them in `afterAll` by visitor id.
- Print "more than 99.9%" instead of "100.0%"; reword "Every challenger (A) beats control B with probability 5% or less".
